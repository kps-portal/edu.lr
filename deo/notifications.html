Scope of Access & What's Actually Confirmed Here
A real notifications table does exist in this schema — dashboard.html already queries it live for the unread-count badge (.from('notifications').select('id', {count:'exact',head:true}).eq('is_read',false)), which confirms an id column and a boolean is_read column. No other page in this codebase reads full notification rows, so no other column is documented anywhere. This page fetches every row from that same table and displays whatever descriptive fields are actually present on each record — it does not invent a fixed set of columns (subject/priority/source, etc.) that might not exist. "Mark as read" writes only to the confirmed is_read column — see "What this page shows" for exactly what was checked.

What this page shows

Storage — a real, live public.notifications table. This page runs select('*') against it (no dedicated columns assumed) and renders each row using whichever of these common field names is actually present: title/subject/message/body for the alert text, category/source/type for the source, priority/severity for the priority pill, and created_at/date/sent_at for the date. Fields that aren't present on a given row are simply left blank — nothing is fabricated to fill a gap.

Mark as read / Mark all as read — write { read: true } to the row(s) via the confirmed read column, the same column dashboard.html already reads for its unread badge. There is no "mark unread" here since the original stub didn't have one and nothing else in the codebase needed it.

No per-user scoping — this table isn't filtered by a recipient/user id anywhere else in the codebase (the dashboard's count query has no such filter either), so this page treats it as district-wide, matching the page's original "District alerts" framing rather than a personal inbox. If this table is meant to be scoped per-account, that would need a schema check this session didn't have access to.

Search and the status filter run entirely client-side over what was fetched — no server-side text search was assumed since the table's text columns aren't confirmed.

DEO can: view every real alert in the notifications table, search/filter them, and mark one or all as read — real reads and writes against Supabase, not a demo.
